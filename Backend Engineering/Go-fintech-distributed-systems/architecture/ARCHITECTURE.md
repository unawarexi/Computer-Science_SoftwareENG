# Architecture & Project Structure Guide

This document outlines the layout, architecture, and design patterns used in the Go Fintech Distributed Banking System. It serves as a map for engineers and AI agents to quickly understand where business logic, data access, and infrastructure code live.

## Architectural Pattern: Clean Architecture

This project strictly adheres to **Clean Architecture** (also known as Ports and Adapters or Hexagonal Architecture). 

The primary rule is the **Dependency Rule**: source code dependencies can only point *inwards*. 
1. **Domain** (innermost) knows nothing about the outside world.
2. **Service** knows about Domain.
3. **API / Infrastructure / Repository** (outermost) know about Service and Domain.

## Directory Layout

### 1. `cmd/`
The main applications for this project. Each subdirectory is a distinct executable.
- `cmd/server/`: The primary HTTP REST API server.
- `cmd/worker/`: Background job worker (consumes Kafka messages, processes outbox events, handles sagas).
- `cmd/migrator/`: Executable responsible solely for running database migrations.
- `cmd/scheduler/`: Cron-like scheduler for periodic tasks (e.g., end-of-day reconciliation).

### 2. `internal/`
Private application and library code. This code cannot be imported by other projects.

#### `internal/domain/` (The Core)
Contains the pure business models and interface definitions (Ports). There are no external dependencies here (no SQL, no HTTP).
- **Files per domain**: Typically contains `model.go` (structs), `repository.go` (data access interfaces), and `service.go` (business logic interfaces).
- **Sub-packages**: `account`, `auth`, `beneficiary`, `card`, `customer`, `fee`, `fraud`, `idempotency`, `kyc`, `ledger`, `notification`, `outbox`, `payout`, `reconciliation`, `saga`, `transaction`, `transfer`, `wallet`, `webhook`.

#### `internal/api/` (Presentation Layer)
Handles incoming HTTP/gRPC requests.
- `api/rest/`: Contains HTTP handlers, the main `router.go`, and `middleware/` (Auth, Rate Limiting, Idempotency, Request Tracing).

#### `internal/service/` (Use Cases)
Contains the concrete implementations of the business logic interfaces defined in `internal/domain/`.
- This layer orchestrates data flow between the repositories and the domain models. 
- **Rule**: Services should never deal with HTTP requests or raw SQL. They only interact with domain models and repository interfaces.

#### `internal/repository/` (Data Access Layer)
Contains the concrete implementations of the repository interfaces defined in `internal/domain/`.
- `repository/postgres/`: Implementations that interact with PostgreSQL (using `sqlc` generated code).
- `repository/mongo/`: Implementations that interact with MongoDB (using the official MongoDB Go driver).

#### `internal/database/` (DB Management & sqlc)
Manages database connections, connection pools, and raw queries.
- `database/postgres/` & `database/mongo/`: Connection pooling and setup logic.
- `database/queries/`: **Raw `.sql` files**. This is where we write our PostgreSQL queries.
- `database/postgres/db_gen/`: **Auto-generated by `sqlc`**. Contains the type-safe Go code generated from `queries/`. **Do not edit manually.**

#### `internal/infrastructure/` (External Adapters)
Handles communication with all external systems other than primary databases.
- `infrastructure/kafka/`: Producers, consumers, and topic management for event streaming.
- `infrastructure/redis/`: Caching and distributed locks (e.g., Redlock).
- `infrastructure/events/`: Internal event dispatcher and types.
- `infrastructure/queues/`: Worker pools and task definitions.
- `infrastructure/mail/`, `infrastructure/pdf/`, `infrastructure/storage/` (S3), `infrastructure/websocket/`, `infrastructure/webrtc/`.

#### `internal/observability/`
Telemetry and monitoring.
- `observability/logging/`: Structured logging (using Zap).
- `observability/metrics/`: Prometheus metric collectors.
- `observability/tracing/`: OpenTelemetry (OTel) distributed tracing spans.

#### `internal/pkg/` (Shared Utilities)
General-purpose utility code that could theoretically be open-sourced.
- `pkg/currency/`: Safe money math (avoiding floating-point errors).
- `pkg/errors/`: Standardized custom error types (e.g., `ErrNotFound`, `ErrInsufficientFunds`).
- `pkg/pagination/`: Cursor-based pagination utilities.
- `pkg/validator/`: Input validation logic.
- `pkg/crypto/`: Hashing and encryption helpers.

---

### 3. Database Schemas & Migrations

#### `migrations/postgres/`
Contains ordered `UP` and `DOWN` raw SQL migration files for PostgreSQL. These define the rigid, ACID-compliant schema for the core banking system (Ledger, Accounts, Transfers, etc.). Managed by `golang-migrate`.

#### `mongo_schemas/`
Contains Go structs equipped with BSON tags that define the shape of documents stored in MongoDB. Used for high-volume, flexible data like `audit_logs`, `session_logs`, and `device_fingerprints`.

---

### 4. Configuration & Deployment

#### Root Level Files
- `sqlc.yaml`: Configuration for the `sqlc` SQL-to-Go code generator. Points to `migrations/` for schema context and `database/queries/` for input queries.
- `Makefile`: Central hub for running commands (`make build`, `make run-server`, `make db-up`, `make sqlc`, `make migrate-up`).
- `.env.example`: Template for environment variables needed to run the app.

#### `deployments/docker/`
- `docker-compose.yml`: Spins up the local development infrastructure (PostgreSQL, MongoDB, Redis, Kafka, Zookeeper, OpenTelemetry Collector, Prometheus).

#### `scripts/`
- Helper scripts for local development (e.g., `seed.go` to populate the database with test data, `generate_keys.go` for JWTs/encryption).

## Data Flow Example (Transferring Funds)

If an agent or engineer wants to trace how money is transferred, this is the path:

1. **Request enters**: `internal/api/rest/router.go` routes POST `/transfers` to the Transfer Handler.
2. **Middleware**: Request passes through `Auth` (validates token) and `Idempotency` (checks if `Idempotency-Key` header was already processed).
3. **Handler**: Parses JSON into a DTO and calls `transferService.InitiateTransfer()`.
4. **Service** (`internal/service/transfer_service.go`): 
   - Validates business rules (e.g., sufficient balance, not sanctioned).
   - Coordinates with `SagaService` to start a distributed transaction.
5. **Repository** (`internal/repository/postgres/transfer_repo.go`): 
   - Uses `sqlc` generated code (`internal/database/postgres/db_gen/`) to execute the raw SQL queries defined in `internal/database/queries/`.
   - Acquires pessimistic locks (`FOR UPDATE`) on the Accounts.
   - Writes to `ledger_entries`, `transfers`, and `outbox_events` within a single PostgreSQL transaction.
6. **Infrastructure** (`internal/infrastructure/kafka/`):
   - The Outbox Relay (running in `cmd/worker/`) picks up the `outbox_events` and publishes them to Kafka for asynchronous notification and reconciliation.
